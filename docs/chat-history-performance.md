# 十万条聊天记录的加载优化

聊天页仍按每页 50 条展示。服务端分别按时间索引读取消息和评估记录，首屏每类最多取 51 个键，再合并为最新一页。消息足够填满候选集时，评估查询只检查可能进入本页的时间范围；较早且已关联到 Bot 消息的评估不再被逐条回扫。精确总数继续在正文返回后独立统计。

原查询把常量记录类型一起放进 `UNION ALL` 排序，SQLite 在大群中会选择 `(GroupId, Id)` 索引后对整群排序，部分来源筛选还会回表访问原始消息。现在首屏和页码查询分别读取有序候选，再合并排序；只有当前页读取正文。来源筛选有对应的部分覆盖索引，决策去重也有发送 ID 覆盖索引；列表查询不加载原始消息段或决策观察窗口。回执关联将空平台 ID 映射为空串，避免可空连接生成 `OR` 后改扫整群留痕。

按 `时间 → 记录类型 → ID` 降序排列的规则、完整 DateTime tick 精度、稳定快照、来源筛选、字面查找和精确消息关联保持原有语义。深分页需要读取截至目标页的键，内存开销随页码增加；正文仍只读取一页。

## 实测

2026-11-17，本地 Windows。优化前基线在 .NET 9 Debug 构建上测得；下表及发布前的最终回归在 .NET 10 Release 构建上复测，测试只使用合成数据与临时 SQLite。单群包含 **10 万条消息 + 2 万条评估记录**，每条消息额外带 2 KiB 原始消息字段，每条评估带 4 KiB 窗口字段，SQLite 页缓存为 8 MiB。

优化前，同一合成单群首次读取约 **396 ms**，各来源 24 次打开的 p50 **329 ms**、p95 **358 ms**，查询计划包含临时排序。

优化后，将测试进程绑定到 **2 个逻辑核心**，设置 `DOTNET_PROCESSOR_COUNT=2`、`DOTNET_GCHeapHardLimit=0x20000000`（512 MiB GC 堆预算）：

| 项目 | .NET 10 Release 复测 |
| --- | ---: |
| 单群首次读取最新 50 条 | 40 ms |
| 单群及全部记录、各来源共 48 次打开 p50 / p95 / 最大 | 3 / 5 / 7 ms |
| 全部 2 万条评估均已关联到消息时的首屏 | 4 ms |
| 跳到最后一页（第 2201 页，含精确总数） | 419 ms |

发布前复测进程峰值工作集 **142 MiB**（16 个逻辑核环境，未绑定 CPU/GC 上限）；上表是同一合成数据集在 .NET 10 Release 上的结果，与早期 .NET 9 受限进程数据数量级一致。每种来源的首屏候选查询均验证没有临时排序。优化前基线未限制 CPU；这些是本地服务读取耗时，不含浏览器渲染、网络传输，也不等同于在实际 2 核 2 GiB 云主机上的端到端验收。

## 回归与复现

在仓库根目录运行：

```sh
dotnet run --project tools/ProactiveCheck -- --chat-history-only
```

该入口同时检查旧库幂等升级、索引列与新库一致、已有记录保留、快照分页、全部来源、发送关联、100 ns 时间边界、空群、深分页及十万条单群的 SQL 查询计划。查询计划验证不依赖计时阈值，能直接阻止整群临时排序重新出现。性能测试输出逻辑核心数、GC 内存预算与进程峰值工作集；它不自行修改系统资源限制。

## 数据影响与回滚

升级只增加 11 个索引：8 个消息来源部分索引、1 个主动消息关联部分索引、2 个评估时间线覆盖索引，不增加列或改写聊天正文。8 个来源索引中，一条消息至多进入全局和单群各一个索引；有发送 ID 的主动消息还进入关联索引。已有库在升级后的首次启动创建索引，会有一次性的磁盘扫描、建索引耗时和索引空间开销，后续启动使用 `IF NOT EXISTS`。

回滚应用版本即可，新索引可以保留，旧程序仍能读取数据库。若需要回收索引空间，可在停止服务并备份数据库后，仅删除本次新增的 `IX_ChatMessages_Timeline_*` 和 `IX_ProactiveChatLogs_Timeline*` 索引；现有业务表和原有索引均无需变更。
